# Configured agent review, revision, and gate

**Scope:** Phase 4 optional machine execution of three independent roles. The submitting backend process chooses the policy once; existing submissions keep that snapshot if configuration changes.

```mermaid
sequenceDiagram
    participant Submitter as API or creation worker
    participant DB as Postgres work queue and content
    participant RoleWorker as Role-specific trusted worker
    participant Provider as Configured role provider
    participant Service as Shared workflow service

    Submitter->>DB: Store exact version and review/gate/revision actor policy
    Submitter->>DB: Enqueue assigned REVIEW_QUESTION
    RoleWorker->>DB: Claim only its assigned role, queue, and item type
    RoleWorker->>Provider: Send bounded exact version and findings
    Provider-->>RoleWorker: Versioned decision or revised content
    RoleWorker->>RoleWorker: Validate role-specific response
    RoleWorker->>Service: Complete with fenced claim and execution provenance
    Service->>DB: Record decision/run and next work in one transaction
    Note over DB: Review approval queues gate; no publication yet
    RoleWorker->>DB: Gate role claims APPROVE_PUBLICATION
    RoleWorker->>Provider: Request gate decision for exact version
    Provider-->>RoleWorker: approve_and_publish, changes_requested, or rejected
    RoleWorker->>Service: Complete gate through shared transition
    Service->>DB: If approved, record gate decision and publication event; move pointer
```

`CONTENT_AGENT_REVIEW`, `CONTENT_AGENT_REVISION`, and `CONTENT_AGENT_GATE` independently enable assignments when a version is submitted. They must be consistent on the API and creation worker because both can submit versions. Each enabled role needs its own `AGENT_WORKER_ROLE` process and provider configuration. An enabled queue waits if that worker is absent. Providers see bounded task data and return JSON; they cannot claim work or write application state.

An agent reviewer cannot review a version generated by that same actor; such a submission goes to a human. An agent gate actor must differ from the reviewer agent; the default human policy still permits sponsor self-review. Review and gate execution runs retain machine/provider provenance. `changes_requested` may route a revision item to the configured reviser, whose accepted output creates a new immutable version and submission under the previous policy. After the third submission, change requests route revision to a human. After three failed machine claims, the sponsor can hand a failed review, revision, or gate item to the human queue; creation failures stay creation requests. A gate provider only proposes a decision: the shared service checks the claim, current version, review approval, and policy before publishing.
