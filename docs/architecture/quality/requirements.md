# Quality requirements

These are architecturally significant expectations from the [implementation plan](../../../architecture-plan.md) and current behavior. They are scoped to v1; no production traffic or availability service level has been specified.

| Area                             | Requirement and acceptance evidence                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Historical correctness           | Editing a question or quiz must leave prior versions and attempts unchanged. Database immutability constraints and integration tests should reject version or snapshot mutation.                                                                                                                                                                                                            |
| Authorization                    | Only owners may change their questions and quizzes; only a learner may read their own attempts and history. Published public content may be discovered, and published unlisted content may be read by ID. API integration tests should cover allowed and denied access.                                                                                                                     |
| Transactional consistency        | Creating a version or attempt and completing an attempt must commit all related records together or none. Multi-step repository operations use `withTransaction`.                                                                                                                                                                                                                           |
| Batch provenance and consistency | A validated, versioned batch artifact and digest must be retained before draft creation. Reusing its sponsor-scoped key with different content must fail. Materialization must create every private draft, tag link, and immutable item mapping atomically; imported versions require review before publication. Contract, service, API, and browser tests cover the applicable boundaries. |
| Runtime data integrity           | API payloads and JSONB domain structures must pass Zod validation at the relevant boundary; database keys and checks must reject invalid relationships.                                                                                                                                                                                                                                     |
| Predictable grading              | Supported v1 answers must evaluate deterministically against frozen snapshots. Awarded points are either zero or the configured points for the current evaluator.                                                                                                                                                                                                                           |
| Observability                    | HTTP requests use structured Pino logging and a request correlation ID; the backend exposes a health route.                                                                                                                                                                                                                                                                                 |
| Maintainability                  | SQL migrations, generated DB types, shared contracts, and generated OpenAPI each have distinct roles. CI runs schema, generated-type consistency, type, lint, test, build, and browser workflow checks for the relevant packages.                                                                                                                                                           |

## Content workflow quality scenarios

| Scenario                                                | Required outcome                                                                                                                         | Evidence                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A newer candidate is saved while a version is published | Bank reads keep the default published version; new quiz memberships may use only versions with publication evidence.                     | [Question-bank service tests](../../../backend/tests/integration/question-bank.database.test.ts) and [quiz membership tests](../../../backend/tests/integration/quizzes.database.test.ts).                                                                                    |
| Content review approves a version                       | The version remains unpublished until a separately claimed final gate approves; stale or duplicate claims cannot create extra decisions. | [Human workflow service tests](../../../backend/tests/integration/content-workflow.database.test.ts).                                                                                                                                                                         |
| A configured provider fails or returns a stale result   | No partial question or decision is stored; role claims are fenced and bounded by retry limits.                                           | [Creation tests](../../../backend/tests/integration/agent-creation.database.test.ts), [agent workflow tests](../../../backend/tests/integration/agent-workflow.database.test.ts), and [provider contract tests](../../../backend/tests/unit/agent-workflow-provider.test.ts). |
| A question batch fails during a later item              | The retained artifact remains, while no partial draft, tag, or key mapping survives.                                                     | [Batch materialization service tests](../../../backend/tests/integration/question-batches.database.test.ts).                                                                                                                                                                  |

The first scenario has a focused service-test gap: current tests verify the bank pointer, publication history, source access, and retained quiz references, but do not combine an older published version and a newer never-published candidate in one new-membership test. This remains a validation task, not a change to the implemented rule.

The frontend covers quiz authoring, taking, results, history, human content work, batch ingestion, and feedback submission. Received feedback review remains available through the API. Browser workflow tests require a Docker-enabled local Supabase stack; their presence does not establish a completed live run in this container.
