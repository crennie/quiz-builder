# Content production workflow and automation foundation

**Status:** Phases 1–4 are implemented. Local validation is complete; full Supabase and browser gates remain pending in an environment with Docker. The [closeout and handover record](content-production-workflow-closeout.md) tracks exact checks and remaining verification. Phase 3 uses human sponsorship and a trusted backend worker as recorded in [ADR-006](../architecture/decisions/ADR-006-sponsored-agent-creation.md); Phase 4 adds configured agent roles as recorded in [ADR-007](../architecture/decisions/ADR-007-configured-agent-review-and-gate.md).

The later [batch artifact ingestion extension](../architecture/decisions/ADR-008-question-batch-artifact-ingestion.md) adds a separate retained-document and materialization path for manually prepared question sets. It does not change the completed provider-worker phases or add quiz automation.

This is the working revision of the proposed content-production plan. It preserves the objective: a human or agent may create, review, or revise questions through the same application-owned workflow. Drafts can remain private indefinitely; publication is deliberate; agent-created content requires review; quiz attempts remain human-only. Read [the existing architecture plan](../../architecture-plan.md) and [current architecture views](../architecture/README.md) before implementation.

## Final gap review and Phase 1 scope

The plan is coherent with the repository once question publication is tracked per version. A single default pointer cannot support the decided rule that any previously published version may be selected for a quiz. Phase 1 therefore uses an append-only publication event table alongside the default pointer. Bank summaries show the default; the published-version endpoint and server-side quiz validation use publication history. Candidate content remains in owner-management endpoints. Publication, unpublication, archive, and restore are explicit owner actions. [ADR-004](../architecture/decisions/ADR-004-question-publication-boundary.md) records the changed invariant.

The remaining design gaps belong to later phases: define who may assign a reviewer or publication gate, when a reviewer may act on their own question, the exact human direct-publish policy once multiple workflows exist, agent ownership and machine authentication, and the policy snapshot format. The queue design must fence lease completion and make domain effects idempotent. None of those decisions should be simulated by a question status. The Phase 1 server policy permits a signed-in owner to directly publish the current version they created; there are no agent identities or review workflows yet. Later phases must replace this single human workflow rule with an explicit policy snapshot before agent creation is enabled. Phase 1 does not claim that content review, ready-to-publish queues, or agent execution already exist.

Before deploying against a database with existing content, check for published rows without a current version and quiz memberships pinned to older versions without publication evidence. The migration backfills only the current version of a published question and preserves historical quiz references. The product owner indicated that existing question data can be discarded, but this migration does not discard it. Regenerate Supabase database types from a running local stack before a live deployment; the repository copy was synchronized for this phase while the local Supabase CLI could not connect to a container runtime.

Phase 1 changes the question API contract: `/questions` and `/questions/:id` now serve only published bank content; `/questions/mine` and `/questions/:id/manage` serve owner candidates. Creation always saves a draft. Publishing uses `POST /questions/:id/publish` with an exact `versionId`; unpublish, archive, and restore are explicit actions. Deploy the migration, backend, shared contracts, and frontend together. Older clients that expect draft content from bank routes or set question status in create/patch payloads must be updated. Apply the migration through the existing Supabase migration workflow before starting the updated API, and run the repository schema check and smoke tests against the target environment.

## Architecture decisions to settle before changing behavior

1. **Question status and publication pointer — decided.** Add `questions.default_published_version_id` with a composite foreign key `(id, default_published_version_id) -> question_versions(question_id, id)`. Keep `current_version_id` as the latest candidate. The new pointer identifies the default version shown in a question summary; it is not the exclusive set of published versions. `questions.status` remains identity-level lifecycle: `draft` requires a null default pointer; `published` requires a non-null pointer; `archived` is excluded from the bank and retains its pointer if one existed. Archiving an unpublished draft leaves its pointer null. Unpublishing clears the pointer and sets `status = draft`. Restoring an archived question is an explicit, authorized, audited transition: restore to `published` if the retained pointer is still eligible under policy, otherwise restore to `draft` with a null pointer. Enforce these relationships in the transition service and with database constraints where practical. No generic metadata patch may perform a publication or restoration transition.
2. **Existing data backfill — decided.** Existing published rows get `default_published_version_id = current_version_id` and a publication-history record for that version; existing draft and archived rows get a null default pointer. No archived question is inferred to have been published. The project owner reports no existing question data that must be preserved, so this should be a no-op in the current environment; still make the additive migration safe for a nonempty database. Check for invalid current-version references before applying it, preserve existing quiz-version references if any, and do not delete data as part of this change. If published legacy rows exist, record the backfill as legacy direct publication without inventing a historical approval decision; older versions without publication evidence remain ineligible for new quiz selection until explicitly published.
3. **What a quiz author may select — decided.** Only question versions with durable evidence of prior publication may be newly added to any quiz, including a draft quiz. This includes older published versions that are no longer `default_published_version_id`; selection must never depend on which version a bank summary happens to show. Never-published drafts are ineligible. The question identity must be currently published at selection time, and the quiz author must have access to that question/version. For the first slice, preserve existing ownership and visibility boundaries: an owner may use their private published question, while another owner cannot see or add it; public published questions are discoverable and unlisted published questions require an explicit ID. Finer version-level grants are deferred, but server-side authorization is not. Enforce publication history and access in the backend when creating or saving a quiz, not only in the picker. Existing immutable quiz versions and attempts retain their exact references if a source is later unpublished or archived. If unexpected legacy quiz data references never-published versions, identify it before migration rather than silently treating those versions as published. This tightens the current quiz-membership rule and needs an ADR.
4. **Review of immutable content — decided.** Review is neither a `questions.status` value nor a mutable `question_versions` status. A review submission binds one exact immutable version, its workflow-policy snapshot, and a review work item. Durable review decisions live in separate records linked to that submission/version; work-item status only describes routing/execution. After either content review or the publication gate returns `changes_requested` or `rejected`, another submission requires a new immutable question version and a new review cycle. A request for changes enqueues a `REVISE_QUESTION` item or equivalent authorized revision task; rejection does not automatically retry. The old version and its decisions remain unchanged; the same version cannot be resubmitted. A stale review may record a decision for its submitted version but cannot approve or publish the new current candidate. Cancel or supersede its pending work item explicitly.
5. **Approval versus publication — decided.** Use separate content-review, publication-gate, and publication service operations with distinct durable decisions/events. Approving content review atomically enqueues an `APPROVE_PUBLICATION` item in a `question-ready-to-publish` queue for the exact reviewed version; it may wait there indefinitely. A final authorized human or independently configured AI gate has three decision outcomes: `approve_and_publish`, `changes_requested`, or `rejected`. On a qualifying approval, the application service transactionally records the gate decision and publication evidence and makes that version the new default in the same transaction. Older published versions remain selectable. `changes_requested` records findings and routes creation of a new version through content review again; `rejected` closes the publication request for that version without publishing it. Either outcome requires a new version for any later submission. An undecided item may remain pending. The gate executor cannot change the pointer directly. Review approval alone never publishes. A human direct-publish workflow remains available where policy explicitly permits it; that action records direct approval and publication and makes the version the new default without a review or ready-to-publish item.
6. **Question visibility and answer exposure.** Public/unlisted published question responses currently include answer and grading configuration by design; [the architecture plan](../../architecture-plan.md) treats answers as practice content. Keep the access boundary on unpublished/restricted content and on quiz attempts. If answer secrecy is a new requirement, treat it as a separate architecture change with changed contracts and UX.
7. **Actors and permissions — decided for trusted workers.** Existing `questions.created_by` and `question_versions.created_by` are non-null UUID foreign keys to `profiles`, whose IDs come from `auth.users`; current owner checks depend on them. Agent-created questions use an authenticated human sponsor as owner, while separate immutable run records identify machine authorship. The trusted backend worker uses fixed role identities and scoped queue claims; providers have no application credentials. There is no collaborator/role model today; retain existing owner and visibility checks until a narrower authorization design is chosen. See [ADR-006](../architecture/decisions/ADR-006-sponsored-agent-creation.md) and [ADR-007](../architecture/decisions/ADR-007-configured-agent-review-and-gate.md).

## Proposed target and boundaries

Publication, review, and work execution answer different questions:

| Concern            | Source of truth                                                    | Meaning                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Question lifecycle | `questions.status` and `default_published_version_id`              | Whether the identity is unpublished, available through its published versions, or archived. A published question may also have a newer candidate. |
| Candidate content  | Immutable `question_versions` and `current_version_id`             | Which content snapshot is being edited, submitted, or considered for replacement. No mutable review status is stored on a version.                |
| Content review     | Submission and decision records for an exact `question_version_id` | Whether that candidate was approved, rejected, or sent back for changes under a recorded policy. Approval is not publication.                     |
| Publication gate   | Gate decision for an exact reviewed version and review decision    | Approve and publish, request changes, or reject. A qualifying approval lets the application service publish.                                      |
| Queue processing   | `work_items` and their events                                      | Whether a bounded task is pending, claimed, completed, failed, or cancelled. Completing a task is not itself a content or publication decision.   |

The existing `archived` question status remains an availability/lifecycle state, not a review outcome. A later cleanup could model archiving separately, but this plan does not require changing that established enum.

For example, a question can be `published` with version 1 as its default published version while version 2 is the latest candidate under review. Approving version 2 records a content-review decision and puts a publication-gate item in `question-ready-to-publish`; version 1 remains available throughout the wait. A qualifying final gate decision publishes version 2, adds it to publication history, and makes it the default; version 1 remains selectable. If review requests changes, the author creates version 3; the question can still remain published through version 1.

- The question bank contains question identities with one or more previously published versions, filtered to `status = published` and by visibility. `default_published_version_id` supplies a summary/default version; it does not define the full version set. Archived questions remain absent even when their pointer is retained. Other users' `public` questions appear in list/detail; their `unlisted` questions appear only through known ID; their `private` questions are restricted to the owner or a future explicit grant. Owner draft management reads `current_version_id` separately. Review reads only the submitted version for an authorized work item. Tags and visibility stay on stable question identity, so changing either can change bank discovery without creating a content version.
- Concretely, the bank list contains the viewer's own eligible questions regardless of visibility and other users' public questions, with the default version as a summary. Bank detail may also show another user's unlisted published question when its ID is known. An authorized bank-version or picker operation may enumerate multiple published versions of a question; neither bank nor picker endpoints reveal never-published drafts. The owner management API can list every owned version, including drafts and older versions, for content management; merely seeing a version there does not make it selectable for a quiz. Selection must query publication history and permissions rather than compare the version ID to `default_published_version_id`.
- Content mutations insert immutable `question_versions` and advance `current_version_id` transactionally. A new candidate never advances `default_published_version_id`. Publication checks actor authority, policy, exact version eligibility, qualifying final gate or permitted direct-human action, and staleness under a row lock; it records publication evidence, updates the default pointer to that version, and writes an audit event in the same transaction.
- Publication also records durable, queryable evidence that the exact version was published. This may be an append-only publication event or a publication ledger backed by events; it must cover direct publication, review-based publication, replacement, and the legacy backfill. A version is not eligible for new quiz selection merely because it is owned, approved, or the latest candidate. Older published versions remain eligible while the question identity is published and the quiz author is authorized.
- Review submissions identify one exact version and store a policy snapshot. Structured decisions include reviewer actor, decision (`approved`, `changes_requested`, `rejected`), findings, timestamp, and optional work-item ID. Source and policy are server determined, not self-reported by a client. The original review requirement survives retries and later configuration changes. Content approval and creation of the ready-to-publish work item are atomic and idempotent. The gate item binds the exact version, qualifying review decision, and publication-policy snapshot. A newer candidate cannot be published through an obsolete gate item. A gate request for changes creates a `REVISE_QUESTION` item or equivalent authorized revision task; the resulting new version must pass content review and the final gate again. A rejected gate item is terminal for that version's publication request; a later attempt also starts with a new version. The queue routes each task; it is not the sole record of either decision.
- Work items are durable, typed requests: `CREATE_QUESTION`, `REVIEW_QUESTION`, `REVISE_QUESTION`, and `APPROVE_PUBLICATION`. Queue identity controls routing; type controls payload and result validation. `APPROVE_PUBLICATION` items route through `question-ready-to-publish` and can remain pending indefinitely. Status and lease state are independent of content-review and publication decisions. Inputs and results use versioned Zod discriminated unions. Bulk enqueue goes through authorized services with bounded request sizes and quota/rate controls; it is not an arbitrary execution endpoint.
- One application service owns the transition from validated work-item result to question-version or review state. It also records the work-item event and resulting domain event transactionally. Human UI and agent worker use the same operations. Work-item completion is fenced by a claim token/generation and a current lease, so a timed-out worker cannot complete after another claimant. Retries are at least once; domain effects are idempotent by operation key. Set bounded retry and review/revision iteration limits and a manual failure path.
- A worker may claim only queues/types allowed by its authenticated identity and scoped permissions. An agent may create a candidate but never directly publish. An agent cannot review its own run. Automated content review and the AI publication gate require independently configured identities/policies and full provenance; the application service alone applies a qualifying gate decision. Provider/model/run metadata belongs in execution provenance, not in core question content.

## Incremental delivery

1. **Publication boundary:** Add pointer, composite constraint, backfill, status consistency, publication/approval audit, durable per-version publication history, and explicit transition service. Split bank, owner management, and authorized published-version picker endpoints/contracts; update feedback eligibility and all question read paths. Update question editor and quiz picker to use the correct projections. Preserve old quiz memberships. Document the changed question lifecycle and quiz-selection rule in an ADR and the smallest affected architecture views.
2. **Human review and queue foundation:** Add typed queues/items, submissions/decisions, publication-gate decisions, actor references, claim lease fencing, retry/cancel/idempotency, and events. Add authorized create/submit/content-review/gate/publish operations and human queue UI. Prove draft, permitted direct human publication, content review, ready-to-publish waiting, final human gate, and revision end to end before agent integration.
3. **Agent creation:** First decide agent-created question ownership, storage, access, and machine identity. Then add a scoped runner contract, validated generation result, and provenance. Agent output creates a candidate and exactly one review item in one transaction. Use a human reviewer initially. Keep provider integration replaceable and outside quiz attempt/scoring paths. Do not implement this phase with a null or dummy `created_by` placeholder absent the chosen schema and authorization design.
4. **Optional agent review/revision/publication gate:** Add independently configured AI content reviewers, revisers, and final publication gate executors after human workflow and queue semantics are stable. A qualifying AI gate decision invokes the same application publication service; it does not grant an agent direct publication authority.

Prefer additive SQL migrations, parameterized `pg` queries, shared Zod contracts, and existing transaction conventions. No ORM, external broker, or general workflow framework is indicated by the current repository.

## Validation gates for later implementation

- Test draft invisibility through list, detail, quiz picker, feedback eligibility, and any new management/review route; owner and assigned reviewer access is scoped correctly. Test public, unlisted, private, and archived behavior separately.
- Test permitted direct human publication and agent mandatory content review with persisted policy snapshots and audit events. Test review of an exact immutable version, stale decisions, revision cycles, and atomic creation of exactly one ready-to-publish item after approval. An approved version must remain unpublished while that item waits. Test final human gate approval, request changes and rejection requiring a new version before resubmission, and optional AI gate approval through the application service.
- Test that the default published version remains visible while a newer candidate is edited or reviewed. Test an atomic default change, visibility of multiple published versions where exposed by the API, and concurrent publication/review requests.
- Test that neither draft nor never-published question versions can be newly added to any quiz, including a draft quiz. Test selection of an older previously published version after the current bank pointer changes, without exposing a newer draft. Test owner private access, other-owner denial, public and unlisted access, retained historical membership, quiz detail and attempt snapshots, and unchanged attempt permission rules. Detect unexpected legacy draft-question memberships before migration.
- Test work-item concurrent claims, lease expiry and fencing, retry exhaustion, duplicate completion, idempotent enqueue, cancellation, malformed results, and role/identity spoofing.
- Run relevant shared, backend, frontend, migration, OpenAPI, and E2E checks as each slice lands. Review the final diff and update architecture/API docs for each changed boundary.

## Open product decisions

Cross-owner reviewer and publication-gate grants, finer version-level access grants, and external worker authentication remain open. The implemented trusted workers use server-chosen role identities and the sponsoring owner's access boundary.
